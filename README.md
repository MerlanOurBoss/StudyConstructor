# Конструктор учебных сценариев

Система для Unity, в которой учебный сценарий собирается без программирования: шаги и порядок описываются в текстовом файле, а режим прохождения, обработка ошибок, журнал и оценка настраиваются в Inspector. Один и тот же сценарий проходится в режимах «Тренировка» и «Экзамен».

**Среда:** Unity 6000.6.5f1, URP. Сторонние ассеты и плагины не используются.

# Инструкция для пользователя

Для работы со сценарием программировать не нужно.

## Как запустить демонстрацию

1. Откройте проект в Unity 6000.6.5f1.
2. В окне **Project** откройте сцену `Assets/Scenario/Demo/DemoScenario.unity`.
3. Нажмите **Play** и выберите режим: **Тренировка** или **Экзамен**.

**Управление:**

| Действие | Клавиша |
|---|---|
| Движение | WASD или стрелки |
| Заглушка: открыть / закрыть (подойти вплотную) | E / Q |
| Кнопка на площадке КН-1: нажать (подойти вплотную) | E |
| Кнопка «Доклад» и «Рычаг» на пульте справа внизу | Мышь |

Слева вверху показаны активные задания. При ошибке вверху появляется красное сообщение с причиной.

## Как изменить сценарий

Сценарий демонстрации лежит в файле `Assets/Scenario/Demo/Scenarios/Scenario.txt`. Его можно открыть в любом текстовом редакторе.

1. Измените файл и сохраните его.
2. В окне **Hierarchy** выберите объект **Scenario**.
3. В Inspector, в компоненте **Scenario Runner**, нажмите **«Сгенерировать сценарии»**.
4. Посмотрите результат под кнопкой: количество шагов по группам либо ошибки с номерами строк. Если в файле есть ошибка, прежний сценарий не меняется.
5. Сохраните сцену: **File → Save**.

Если файл изменён, а кнопка не нажата, инспектор предупредит об этом.

### Команды файла

```text
// Комментарий: всё после двух косых черт. Строки на # и \\ тоже считаются комментариями.

start_group:Группа 1
    start_parallel
        set_action_number:1.1
        exec:P_PF_3*#[291-VW-M-01]*#1
        exec:P_PF_3*#[291-VW-M-02]*#1
    stop_parallel
stop_group

start_group:Группа 2
    start_continuous
        exec:P_PF_3*#[291-VW-M-05]*#1
        exec:P_PF_3*#[291-VW-M-05]*#0*#if:[291-VW-M-06]=1
    stop_continuous
stop_group
```

| Команда | Что значит |
|---|---|
| `exec:<механика>*#[<объект>]*#<значение>` | Шаг: что нужно сделать. Значение можно не писать, тогда будет `1` |
| `...*#if:[<объект>]=<значение>` | Необязательное условие: действие засчитывается, только если другой объект в нужном состоянии. Иначе это нарушение |
| `start_parallel` … `stop_parallel` | Шаги внутри доступны сразу, в любом порядке |
| `start_continuous` … `stop_continuous` | Шаги внутри доступны строго по очереди |
| `start_group:<название>` … `stop_group` | Группа. Группы идут по очереди, в экзамене нарушения считаются внутри группы |
| `forbid:<механика>*#[<объект>]*#<значение>*#<сообщение>` | Запрещённое действие. Значение и сообщение необязательны; без значения запрещено любое действие с объектом. Внутри блока запрет действует, пока активен блок, а вне групп — на весь сценарий |
| `set_action_number:<номер>` | Номер перед текстом следующих шагов блока |
| `set_action_name:<текст>` | Название перед текстом следующих шагов блока |

Блоки можно вкладывать друг в друга. Содержимое группы (и файла без групп) выполняется сверху вниз по очереди. Если в файле есть хотя бы одна группа, все шаги должны быть внутри групп.

Команды `goto:`, `set_step_number:`, `set_operation_number:` и `set_operation_name:` не поддерживаются и пропускаются с предупреждением. `start_condition:`, `start_true`, `start_false` и `start_global_check:` считаются ошибкой, потому что без них сценарий исполнялся бы неверно.

### Механики

Объект в скобках ищется **по имени в Hierarchy**. Имя объекта с механикой должно быть уникальным.

| Код | Что это | Значения | Компонент (Add Component → Scenario) |
|---|---|---|---|
| `P_PF_3` | Заглушка | `1` — открыть, `0` — закрыть | Mechanics → Plug (P_PF_3) |
| `P_BT_1` | Кнопка на площадке | `1` | Mechanics → Button (P_BT_1) |
| `P_TC_1` | Зона (Collider с галочкой Is Trigger) | `1` — войти, `0` — выйти | Mechanics → Zone (P_TC_1) |
| `BUTTON` | UI-кнопка | `1` | Sources → Button Source |
| `COLLISION` | Столкновение с объектом | `1` | Sources → Collision Source |
| `EVENT` | Любой UnityEvent: в списке события выберите компонент и метод `Fire()` | `1` | Sources → UnityEvent Source |

Условие `if:` работает только с механиками, у которых есть состояние: заглушкой (`1` — открыта) и зоной (`1` — игрок внутри).

Для зон и столкновений у игрока должны быть тег `Player` и `Rigidbody`. Для заглушки и кнопки на площадке нужен Collider, иначе игрок не сможет взаимодействовать с объектом.

## Как изменить порядок и группы

**В файле:** переставьте строки или блоки и сгенерируйте сценарий заново. Это основной способ.

**Мышью:** раскройте в Hierarchy объект **Scenario → Scenario** (сгенерированный сценарий):

- перетащите шаг или блок, чтобы поменять порядок;
- снимите галочку активности у объекта, чтобы шаг или блок пропускался;
- у **Flow Block** галочка **Parallel** переключает «одновременно» и «по очереди»;
- у **Flow Step** можно изменить текст задания, условие и запреты.

> **Важно:** повторная генерация заменяет иерархию содержимым файла, и правки мышью пропадут. Постоянные изменения вносите в файл.

## Как настроить режим

Режимы находятся в компоненте **Scenario Runner → Modes**:

| Поле | Что настраивает |
|---|---|
| **Name** | Название режима |
| **Rules** | Обработка ошибок. «Тренировка» — шаг можно повторить. «Экзамен» — шаг получает Failed; поле **Violation Threshold** задаёт порог пропуска группы (по умолчанию 2) |
| **Out Of Order** | Действие шага, очередь которого не наступила: «Считать нарушением» или «Игнорировать (шаг неактивен)» |
| **Script** | Файл сценария |
| **Ignore Groups** | С галочкой группы файла не учитываются: весь сценарий идёт одной группой |
| **Flow** | Сгенерированный сценарий, заполняется кнопкой |
| **Analyzer** | Как оценивается результат; баллы и штрафы настраиваются здесь же |

В демонстрации оба режима используют один файл, поэтому шаги не дублируются. У «Тренировки» включён **Ignore Groups**. Если порядок в режимах должен отличаться, укажите режиму отдельный файл.

Список **Loggers** в том же компоненте задаёт, куда записывается журнал: **JSON-файл** и/или **Консоль Unity**.

**Новая кнопка на экране.** Интерфейс лежит на сцене под объектом **UI**. Чтобы добавить режим в меню, продублируйте кнопку в **Menu** и укажите в её **OnClick** метод `StartMode` с номером режима (с нуля). Для ещё одного анализатора продублируйте кнопку в **Results → Analyzers**, укажите `SelectAnalyzer` с его номером и добавьте кнопку в список **Analyzer Buttons** компонента **Scenario Hud**.

## Как посмотреть журнал и результат

После прохождения или кнопки **«Завершить досрочно»** откроется экран результата:

- **итог и строки по шагам** — показываются сразу;
- **кнопки анализаторов** — заново оценивают тот же журнал другим анализатором, проходить сценарий не нужно;
- **«Журнал»** — все события с временем;
- **«Пройти заново»** и **«В меню»**.

В меню кнопка **«Сохранённые журналы»** открывает файлы прошлых прохождений. Их тоже можно оценить любым анализатором. На Windows файлы лежат в `%USERPROFILE%\AppData\LocalLow\DefaultCompany\StudyConstructor\ScenarioLogs`.

Если данных в журнале не хватает (например, прохождение завершено досрочно), оценка всё равно показывается, а ниже появляются предупреждения.

## Контрольные примеры

**Тренировка — 15 баллов за три шага:**

1. На заглушке 01 нажмите **E** — 10 баллов.
2. На заглушке 02 нажмите **Q**, затем **E** — 5 баллов.
3. На заглушке 03 нажмите **Q**, **Q**, затем **E** — 0 баллов.

Всего в сценарии 17 шагов, максимум в тренировке — 170 баллов.

**Экзамен — 70 баллов:**

1. В «Группе 1» нажмите **Q** на заглушках 01 и 02. Они получат Failed, а 03 и 04 — Skipped.
2. Остальные группы пройдите без ошибок.
3. Штраф 20 + 10 = 30, итог 100 − 30 = 70.

**Смешанная активация (сценарий демонстрации):**

| Часть | Как активируется |
|---|---|
| Заглушки 01–04 | Одновременно, в любом порядке |
| Заглушки 05, 06, 05, 06 | По очереди |
| Заглушки 07 и 08 | Две ветки: каждая по очереди, между собой в любом порядке. Закрыть 07 можно, только пока 08 открыта |
| Рычаг, ящик, КН-1, «Доклад», «Выход» | Одновременно |

**Смена настроек без правки кода:** снимите **Ignore Groups** у «Тренировки» или выберите другой **Analyzer**. Шаги и файл при этом не меняются.

# Техническое описание

## Части системы

Весь код находится в `Assets/Scenario`.

| Часть | Классы | За что отвечает |
|---|---|---|
| **Механики** | `EventSource`, `PlugMechanic`, `ButtonMechanic`, `ZoneMechanic`, `ButtonSource`, `CollisionSource`, `UnityEventSource` | Сообщают о действии на объекте сигналом `ScenarioSignal`. О шагах ничего не знают |
| **Генерация** | `ScriptParser`, `FlowGenerator`, `ScenarioRunnerEditor` | Превращают текст в иерархию объектов в редакторе и показывают ошибки |
| **Сценарий** | `ScenarioFlow`, `FlowGroup`, `FlowBlock`, `FlowStep`, `StepCondition`, `ActionCondition`, `ViolationRule` | Что и в каком порядке делать. Шаг отвечает только на вопрос, как сигнал соотносится с ним (`StepCheck`) |
| **Режим** | `ScenarioMode`, `ExecutionRules`, `TrainingRules`, `ExamRules` | Настройки прохождения и решения об ошибках |
| **Исполнение** | `ScenarioRunner`, `ScenarioRun`, `StepRuntime`, `GroupRuntime` | Активация шагов по иерархии, статусы, события. Состояние прохождения хранится отдельно от объектов сцены |
| **Журнал** | `RunRecorder`, `RunLog`, `LogEntry`, `ScenarioLogger`, `JsonFileLogger`, `ConsoleLogger`, `RunLogStorage` | Переводит события прохождения в записи и передаёт логгерам |
| **Анализ** | `ResultAnalyzer`, `TrainingScoreAnalyzer`, `ExamPenaltyAnalyzer`, `RunLogReader`, `AnalysisReport` | Считает оценку только по журналу, отдельно от прохождения |
| **Интерфейс** | `ScenarioHud`, `PlayerInteractor`, `DemoPlayer` | Демонстрация: экран, ввод, движение |

Сборки: `Scenario.Runtime` (ядро, зависит только от Unity и UGUI), `Scenario.Editor`, `Scenario.Demo`.

## Как проходит одно действие

```text
Игрок нажал E
  → PlugMechanic.Raise("1")                 сигнал от объекта
  → ScenarioRunner → ScenarioRun.Handle     передача прохождению
  → FlowStep.Check                          запреты, затем условие шага
  → ExecutionRules                          решение при нарушении
  → Advance                                 активация следующих шагов
  → события → RunRecorder (журнал) и ScenarioHud (экран)
В конце: Finished → журнал сохранён → анализатор режима считает оценку
```

Части связаны тремя контрактами: `ScenarioSignal`, `StepCheck` и `LogEntry`. Режим, логгер и анализатор настраиваются независимо, отдельного кода под их сочетания нет.

## Принятые решения

- **Генерация в редакторе, а не при запуске.** Результат виден в Hierarchy, его можно проверить и поправить мышью, а ошибки файла видны до запуска.
- **Действие вне очереди.** Нарушение засчитывается ближайшему неактивному шагу с этим действием, только если действие не относится ни к одному активному шагу. В тренировке это добавляет попытку этому шагу.
- **Нарушение шага из будущей группы на экзамене.** Шаг сразу получает Failed и учитывается в пороге своей группы. Если к началу группы порог уже достигнут, она пропускается.
- **Одно действие — одно нарушение**, даже если оно запрещено нескольким активным шагам.
- **Выход из зоны не считается неверным действием**, когда шаг требует входа: игрок просто перемещается по площадке (`WrongValueIsViolation`).

## Журнал

`LogEntry` содержит время, тип, Id шага, результат и список дополнительных полей. Тип — строка, а анализаторы читают журнал через `RunLogReader`, который пропускает незнакомые типы. Поэтому новые поля и типы записей не ломают существующую обработку.

Типы записей: `RunStarted`, `StepRegistered`, `GroupStarted`, `StepStatus`, `Violation`, `RunFinished`.

## Как расширить систему

### Новая механика

Базовые классы менять не нужно.

```csharp
using UnityEngine;

namespace StudyConstructor.Scenario
{
    [AddComponentMenu("Scenario/Mechanics/Lever (P_XX_1)")]
    public class LeverMechanic : EventSource
    {
        public override string Mechanic => "P_XX_1";
        public override bool IsValidValue(string value) => value is "0" or "1";
        public override string Describe(string value) => value == "1" ? $"Поднять {name}" : $"Опустить {name}";

        public void Switch(bool up) => Raise(up ? "1" : "0");
    }
}
```

Повесьте компонент на объект, и механика доступна в сценарии: `exec:P_XX_1*#[Имя объекта]*#1`. Чтобы её можно было использовать в `if:`, переопределите `CurrentValue` и `DescribeState`. Для действий вблизи игрока реализуйте `IInteractable`.

### Новый логгер, анализатор или правила режима

Унаследуйте базовый класс и добавьте `[Serializable]`. Реализация сама появится в выпадающем списке Inspector, имя пункта задаётся атрибутом `[DisplayName]`.

| Что добавить | Базовый класс | Что реализовать |
|---|---|---|
| Логгер | `ScenarioLogger` | `Begin`, `Write`, `End` |
| Анализатор | `ResultAnalyzer` | `Evaluate(RunLog)`, для чтения журнала есть `RunLogReader` |
| Правила исполнения | `ExecutionRules` | `StatusAfterViolation`, при необходимости `ShouldSkipRest` |

### Новый тип шага

Создайте наследника `StepCondition` с `[Serializable]`: он сразу доступен в поле **Condition** у `FlowStep`. Чтобы задавать его из текста, добавьте команду в `ScriptParser`. Это единственное расширение, требующее правки существующего кода.

# Что улучшил бы дальше

**Ограничения текущего решения:**

- Сценарий пишется в текстовом редакторе, а в Unity выполняются генерация и настройка. Отдельного визуального редактора нет.
- Повторная генерация заменяет ручные правки иерархии.
- Новая команда сценария требует правки `ScriptParser`.
- Механики собираются при включении `ScenarioRunner`, поэтому объекты, созданные во время игры, не учитываются.
- Группы экзамена идут строго друг за другом.

**Идеи развития:**

- реестр команд, чтобы добавлять их без правки `ScriptParser`;
- команды ветвления и переходов: `start_condition`, `goto`;
- перекрывающиеся и одновременно активные группы;
- окно редактора с деревом сценария и сохранением правок обратно в файл;
- автоматические тесты контрольных примеров.

**Сознательно не реализовано:** 3D-графика, анимации и сетевая часть (не требуются по заданию). Корректность проверяется на демонстрационной сцене.

# Ход работы и затраченное время

Основная часть работы закоммичена логическими частями после реализации, а не по мере готовности каждой части.

**Фактически затраченное время:** 5 часов
